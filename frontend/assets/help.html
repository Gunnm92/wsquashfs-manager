Bien démarrer

Ce gestionnaire transforme tes dossiers de jeux Windows en images .wsquashfs, puis t'aide à les régler et à les entretenir. Le lancement lui-même est fait par wsquashfs-launcher.

  1. EmpaqueterUn dossier de jeu devient une image : un seul fichier compressé, en lecture seule. → Ajouter un jeu
  2. EssayerLe lancement d'essai démarre le jeu sur la machine de jeu et rapporte ce qu'il a vu (à activer dans Réglages). → Un jeu ne se lance pas
  3. AjusterLes réglages du jeu sont dans son autorun.cmd, modifiable depuis la fiche. → Changer un réglage

Les mots à connaître

Image
Le jeu compressé en un fichier .wsquashfs. Elle n'est jamais modifiée par le jeu.
autorun.cmd
La petite fiche, dans l'image, qui dit quoi lancer et avec quels réglages.
Sauvegardes
Tout ce que le jeu écrit (parties, options), gardé à part dans saves/<jeu>.
Surcharge
Un réglage essayé à côté de l'image, sans la reconstruire. Batocera ne le voit pas.
.old
L'ancienne version d'une image, gardée après une modification jusqu'à ce que tu la valides.
Runner
Le Wine ou le Proton qui fait tourner le jeu Windows sous Linux.
Rien n'est jamais détruit sans confirmation : une image modifiée est reconstruite à côté, et l'ancienne reste en .old tant que tu ne l'as pas validée.

Guides

Les tâches courantes, étape par étape. Clique sur un guide pour l'ouvrir.

Ajouter un jeu
  1. Copier le dossier du jeu dans roms/<système>/, nommé Mon Jeu.pc (ou .wine s'il contient déjà un prefix Wine).
  2. Facultatif : l'essayer avant de l'empaqueter avec wsquashfs-launcher "Mon Jeu.pc". Un dossier .pc est monté comme le sera son image : il n'est jamais modifié, prefix et sauvegardes vont dans les sauvegardes de Mon Jeu, reprises ensuite par l'image.
  3. Ouvrir l'onglet Dossiers à empaqueter, cocher le dossier puis Analyser et empaqueter.
  4. Relire l'autorun proposé : l'exécutable choisi et la raison de chaque réglage sont indiqués. Corriger si besoin.
  5. Empaqueter : la tâche part dans la file (ou cette nuit). L'image est vérifiée à la fin ; le dossier est renommé en .wine, et supprimé seulement si tu l'as demandé.
Un jeu ne se lance pas
  1. Fiche du jeu → Lancement d'essai : le jeu démarre sur la machine de jeu (Réglages → Machine de jeu), puis le rapport donne les fenêtres ouvertes, les erreurs reconnues et une capture.
  2. Message failed to open umu.exe ? Fiche → Infos → Liens du runner → Analyser : la réparation est proposée.
  3. Chercher l'erreur dans Dépannage.
  4. Essayer un autre réglage (guide suivant) : par exemple WINE=system pour un vieux jeu 32 bits, ou DXVK=0 pour un problème d'affichage.
Changer un réglage d'un jeu
  1. Fiche du jeu → Modifier l'autorun. La fiche passe en mode édition (cadre orange) : rien n'est écrit tant que tu n'enregistres pas.
  2. Modifier une valeur, ou Ajouter un réglage. Chaque réglage est expliqué dans Réglages de l'autorun.
  3. Essayer sans reconstruire : le réglage s'applique au prochain lancement, en quelques secondes. Batocera, lui, ne le voit pas.
  4. Quand le jeu marche : Reconstruire l'image pour inscrire le réglage dedans. L'ancienne image est gardée en .old.
Installer une nouvelle version ou un patch
  1. Déposer la nouvelle version (ou le patch) dans un dossier du serveur.
  2. Fiche du jeu → Nouvelle version, indiquer ce dossier.
  3. Aperçu : la liste des fichiers ajoutés, remplacés et supprimés, et la place disque nécessaire.
  4. Mettre à jour. L'ancienne image est gardée en .old.
Valider ou annuler une modification (.old)
  1. Après une reconstruction ou une mise à jour, la fiche affiche « Une ancienne version est conservée ».
  2. Lancer le jeu pour vérifier qu'il marche toujours.
  3. Valider supprime l'ancienne version ; Revenir à l'ancienne annule la modification.
  4. Pour plusieurs jeux à la fois : les sélectionner, puis Valider les .old.
Faire le travail pendant la nuit
  1. À côté de chaque bouton qui lance un travail, une petite icône indique quand : éclair = tout de suite, lune = cette nuit. Un clic bascule.
  2. La plage de nuit se règle dans Réglages.
  3. Une tâche prévue la nuit peut être lancée tout de suite depuis Tâches, en haut à droite.

Prefix Wine (Batocera)

Le format de Batocera : jeux arcade et jeux PC préparés pour lui, avec leur prefix Wine complet. L'image reste lisible par Batocera telle quelle.

MonJeu.wine/
├── autorun.cmd
├── system.reg  user.reg
└── drive_c/MonJeu/game.exe
DIR=drive_c/MonJeu
CMD=game.exe
En savoir plus
  • Runner : wine-tkg par défaut. WINE=system pour un jeu 32 bits qui échoue sous wine-tkg (non WoW64) mais passe avec le Wine WoW64 du système.
  • La racine de l'image est le prefix : DIR est relatif à cette racine.
  • Des fichiers *.reg à la racine sont importés au lancement.
  • Batocera ignore les clés qu'il ne connaît pas (GAME_VERSION, WINE…).

Prefix Proton

Un prefix créé par Heroic, Steam ou umu : jeux PC récents. Le jeu est lancé par le même Proton, via umu.

MonJeu.wine/
├── autorun.cmd
├── config_info  pfx -> .
└── drive_c/MonJeu/Bin/game.exe
DIR=drive_c/MonJeu/Bin
CMD=game.exe
En savoir plus
  • Runner : le Proton qui a créé le prefix (1re ligne de config_info), sinon le repli décrit dans Choix automatique du runner.
  • PROTON=<nom> impose un Proton ; s'il est introuvable, c'est une erreur, sans repli silencieux.
  • Les DLL de Proton sont des liens vers le runner (PROTON_DLL_COPY vide), pas des copies.
  • Batocera n'a pas umu : ces images n'y sont pas prévues.

Jeu seul

Seulement les fichiers du jeu. Le prefix est créé au premier lancement, dans les sauvegardes : l'image reste légère.

MonJeu/
├── autorun.cmd
└── game/run me.exe
CMD="game/run me.exe" --arg
En savoir plus
  • Le prefix est créé par Proton via umu (proton-cachyos, sinon l'UMU-Proton le plus récent, sinon GE-Proton).
  • CMD est relatif à la racine ; guillemets si le chemin contient des espaces.
  • WINE=tkg pour garder un prefix Wine. Un prefix Wine déjà présent dans les sauvegardes reste sous Wine : réinitialiser les sauvegardes du jeu pour passer sous Proton.

Runner joint à l'image

Pour un jeu qui ne marche qu'avec un runner précis (Proton modifié pour lui, Wine particulier d'un jeu arcade) : le runner est copié dans l'image, qui devient autonome. Possible avec les trois types.

MonJeu.wine/
├── autorun.cmd
├── runners/Proton-MonJeu-11.0/
└── drive_c/ …
PROTON=Proton-MonJeu-11.0
À réserver aux runners propres à un jeu. Un Proton standard (UMU-Proton, GE-Proton, proton-cachyos) n'a pas à être joint : compter ~250 Mo de plus par image.
Comment le runner est choisi
  • PROTON=<nom> ou WINE=<nom> cherchent d'abord runners/<nom>/ (aussi runners/wine-<nom>/, casse ignorée), puis les runners de la machine. Sans clé, un runner seul dans runners/ est utilisé.
  • Priorité : --wine > runner joint > runners de la machine.
  • Runner nommé introuvable : le lancement s'arrête avec un message, le jeu ne part pas sous un autre runner.
  • Utilisé en lecture seule depuis l'image : Proton n'écrit rien dans les sauvegardes.
  • RUNNER= ne sert qu'aux chemins absolus de la machine.
  • Batocera ignore runners/.
Liens du prefix (erreur failed to open umu.exe)

Dans un prefix Proton, les DLL de Wine sont des liens vers le runner. Ils doivent pointer en relatif dans runners/<nom>/ (ex. ../../../runners/<nom>/files/lib/wine/…). Un lien vers un autre emplacement est cassé ailleurs, et Proton ne le répare pas.

« Dossiers à empaqueter » réécrit ces liens tout seul. Sur une image existante : fiche → Infos → Liens du runner → Analyser, puis la réparation proposée.

À la main : find MonJeu.wine -type l -lname '*compatibilitytools.d*' doit être vide.

Correctif du jeu dans le runner (protonfix)

Un Proton joint peut porter un protonfix, script Python que Proton exécute avant chaque lancement. GAMEID désigne le script :

runners/<Proton>/protonfixes/gamefixes-umu/umu-monjeu.py
PROTON=<Proton>
ENV=GAMEID=umu-monjeu
  • main() fait la préparation (un sys.exit(1) arrête le lancement), puis peut lancer un fil pour le patch à chaud, qui vit jusqu'à la fin du jeu.
  • N'agir que si l'exécutable du jeu est dans sys.argv : umu sert aussi à d'autres commandes.
  • Pour tout runner, Wine compris : PRE= et ATTACH= de l'autorun.

Réglages de l'autorun

L'autorun.cmd est un fichier texte à la racine de l'image : une ligne RÉGLAGE=valeur par réglage. Seul CMD est obligatoire. Clique sur un réglage pour le détail.

L'essentiel

CMDLe programme à lancer obligatoire"My Game.exe" -fullscreen
Exécutable et arguments ; guillemets si le nom contient des espaces.
DIRLe dossier du programmedrive_c/Game
Relatif à la racine de l'image. Vide : la racine.
GAME_VERSIONLa version du jeu, pour s'y retrouverv2.1.0 GOG
Affichée au lancement, par --info, --pack, --install et ici. Ignorée par Batocera.

Wine ou Proton

Sans ces réglages, le runner est choisi automatiquement : c'est le mieux dans la plupart des cas.

WINEImposer une version de Winetkg · system
Wine joint à l'image (runners/<nom>/), sinon /opt/wine-<nom>/bin/wine ou un runner installé. system : le Wine WoW64 du système, utile aux vieux jeux 32 bits. Introuvable : erreur.
PROTONImposer une version de ProtonGE-Proton9-20
Proton joint à l'image, sinon un Proton de Heroic ou Steam (nom du dossier ou version). Introuvable : erreur, pas de repli sur un autre Proton.

Chemin absolu uniquement. Un runner joint à l'image passe par PROTON ou WINE.
ARCHPrefix 32 ou 64 bitswin32
Déduit du prefix existant, win64 sinon.

Manettes, langue, environnement

HIDRAWManette Sony gérée par le jeu lui-même1 · bt

Par défaut, la manette est vue comme une manette Xbox (XInput), comme sous Batocera. À changer seulement pour un jeu qui gère la DualSense lui-même (sans Steam Input) :

  • 1 : manette Sony par hidraw ; une DualSense Bluetooth est présentée en USB (dualsense-usb-bridge), car certains jeux refusent la Bluetooth. Repli XInput si illisible.
  • bt : DualSense Bluetooth en direct, pour un jeu dont les vibrations haptiques passent par la Bluetooth.

Sous GE-Proton, le mode XInput passe aussi par hidraw (PROTON_SONY_HIDRAW_XINPUT=1, posé par le lanceur).

LANGLa langue du jeufr_FR.UTF-8
Posée dans LC_ALL.
ENVVariables d'environnement en plusVAR1=a VAR2=b
Séparées par des espaces. Une surcharge ou un _defaults.autorun ajoute ses variables à celles de l'image au lieu de les remplacer ; -VAR en retire une, ENV= vide les retire toutes.

Touches clavier : un fichier <jeu>.wsquashfs.keys à côté de l'image associe des boutons de manette à des touches.

Sauvegardes à part

Tout ce que le jeu écrit va déjà dans ses sauvegardes. Ces deux réglages relient en plus des sauvegardes à saves/<système>/<jeu>, comme Batocera.

SAVEDIRLe dossier de sauvegarde du jeudrive_c/game/saves
Les sauvegardes empaquetées y sont copiées sans jamais écraser l'existant.

Plusieurs fichiers séparés par ;, relatifs au prefix.

Avancé : commandes autour du jeu

Ces commandes s'exécutent sur la machine, hors de Wine : seulement pour des images de confiance. Batocera et --exec les ignorent.
PREUne commande avant le jeush pre.sh
Lancée une fois, dans DIR, avec l'utilisateur et l'environnement du jeu (WINEPREFIX…). Un échec arrête le lancement. Sert à préparer des fichiers que l'image ne peut pas contenir tels quels.
ATTACHUne commande pendant le jeush attach.sh
Lancée une fois le processus du jeu trouvé ; GAME_PID contient son PID. Elle accompagne le jeu jusqu'à la fin de ses processus Wine, a ensuite 5 s pour finir, puis est arrêtée avec tout ce qu'elle a lancé.
ATTACH_PROCESSLe processus qu'attend ATTACHGame.exe
15 caractères au plus. Défaut : l'exécutable de CMD ; à renseigner quand CMD est un lanceur qui démarre le vrai jeu.

Pour aller plus loin

Essayer un réglage sans reconstruire (surcharge)

Un fichier <jeu>.wsquashfs.autorun à côté de l'image, au même format. Ses réglages l'emportent sur ceux de l'image ; RÉGLAGE= vide revient au défaut du lanceur. C'est ce qu'écrit « Essayer sans reconstruire ».

# Le Jeu.wsquashfs.autorun
HIDRAW=1

Batocera ne le lit pas : une fois le réglage validé, reconstruire l'image (ou « Inscrire les surcharges » sur une sélection).

Le lanceur lit aussi, du plus faible au plus fort : ~/.config/wsquashfs/defaults.autorun (la machine), les variables WSQUASHFS_*, _defaults.autorun dans le dossier du jeu (tous les jeux du dossier), l'autorun.cmd de l'image, la surcharge, puis --set RÉGLAGE=valeur. wsquashfs-launcher --show donne la valeur finale de chaque réglage et sa provenance.

Choix automatique du runner

Sans WINE, PROTON, RUNNER, runner joint ni --wine :

  • Prefix Proton : la même version de Proton (Heroic, Steam, /usr/share/steam/compatibilitytools.d), sinon proton-cachyos, puis l'UMU-Proton le plus récent, puis GE-Proton, puis n'importe quel Proton. Lancé via umu, comme Heroic ; sans umu, le Wine du Proton est lancé directement (WSQUASHFS_UMU=0 force ce mode).
  • Jeu seul : proton-cachyos, sinon UMU-Proton, sinon GE-Proton. Les deux premiers gèrent la DualSense en manette XInput avec vibrations ; GE-Proton la force en hidraw.
  • Autres prefixes (arcade Batocera) : wine-tkg, puis wine-ge/lutris, puis wine-proton, puis le Wine du système.

Les DLL que Proton copie d'ordinaire dans chaque prefix (~190 Mo par jeu) y sont des liens ; ENV=PROTON_DLL_COPY=<motifs> pour un jeu qui doit les remplacer. Le lanceur ramène la pile à 8 Mo si elle est illimitée (Docker sur Unraid), sans quoi proton-cachyos ne démarre pas.

Le lanceur

wsquashfs-launcher monte l'image et lance le jeu, sans aucun privilège. Le gestionnaire s'en sert ; tu peux aussi l'utiliser en ligne de commande.

Commandes

wsquashfs-launcher <jeu.wsquashfs>Lancer le jeu.
--info <jeu.wsquashfs>Version, type, runner, commande et taille, sans monter l'image.
--pack <Jeu.wine>Créer une image à partir d'un dossier.
--exec <jeu> <programme>Lancer un autre programme dans le prefix du jeu (winecfg, regedit, l'outil de config du jeu…).
--listLes jeux connus et leur état.
--doctorVérifier l'installation (aussi visible dans Réglages).
Toutes les commandes
wsquashfs-launcher [--wine <version>] <jeu.wsquashfs | dossier>
Lance le jeu. Un dossier .pc contenant autorun.cmd est essayé en overlay, comme son image, sans être modifié ; un autre dossier (.wine, jeu installé) est lancé sur place, sans montage.
--exec <jeu.wsquashfs> <programme> [arguments…]
Exécutable du jeu (chemin relatif au prefix ou au DIR, casse ignorée) ou outil Wine (winecfg, regedit, cmd, explorer, control joy.cpl…). PRE/ATTACH ne sont pas lancés.
--mount <jeu> · --umount [<jeu>]
Monter le jeu pour le modifier à la main (les changements vont dans ses sauvegardes) ; démonter un jeu ou tous.
--pack <Jeu.wine> [sortie.wsquashfs]
Crée une image (zstd). Une image existante n'est remplacée qu'une fois la nouvelle construite, après confirmation au terminal.
--install <jeu.wsquashfs> [dossier]
L'inverse de --pack : extrait le jeu pour jouer sans FUSE. L'image est conservée, un dossier existant n'est jamais écrasé.
--clean
Supprime le cache, les doublons des sauvegardes (fichiers recopiés sans modification) et les anciennes archives de ~/.local/share/wsquashfs/backups/. Ce que le jeu a écrit est gardé.
--clear [jeu]
Radical : ne garde que drive_c/users des sauvegardes, sans archive. Scores et réglages écrits ailleurs sont perdus.
--saves [jeu]
Copie les sauvegardes de partie (Documents, Saved Games, AppData) de tous les jeux, ou d'un seul, dans saves/<système>/<jeu> à côté de roms/. Sens unique, rien n'est supprimé. Restauration, jeu arrêté : cp -a saves/<système>/<jeu>/drive_c ~/.local/share/wsquashfs/saves/<jeu>/
--wine <version>
Impose un runner (nom ou partie du nom, chemin d'un binaire wine, ou system), avant tout autre choix.
MangoHud, gamemode…
Se placent devant la commande : mangohud wsquashfs-launcher MonJeu.wsquashfs.

Fonctionnement

Modes de montage

Choisis automatiquement à chaque lancement :

  • overlay noyau (par défaut) : overlay du noyau dans un namespace utilisateur ; lectures aléatoires environ 5 fois plus rapides, rien d'orphelin après un plantage. Requiert Linux ≥ 5.11 et squashfuse ≥ 0.5.
  • overlay FUSE (repli, et --mount) : squashfuse + fuse-overlayfs.
  • copy : FUSE bloqué (conteneur sans CAP_SYS_ADMIN) ; copie de travail en cache.
  • dossier : prefix .wine ou jeu installé par --install, lancé sur place. Un dossier .pc passe, lui, par l'overlay FUSE.

Tout échec de l'overlay noyau retombe sur fuse-overlayfs ; --doctor dit pourquoi. Les deux partagent les mêmes sauvegardes.

Où sont les données 
~/.local/share/wsquashfs/
├── saves/<jeu>/     ce que le jeu a écrit
└── wine/ dxvk/ …    runners et traducteurs installés
~/.cache/wsquashfs/  montages et copies de travail

À côté de l'image : <jeu>.wsquashfs.autorun (surcharge) et <jeu>.wsquashfs.keys (touches). À côté de roms/ : saves/<système>/<jeu>.

Variables d'environnement
WSQUASHFS_SAVES_DIR, WSQUASHFS_CACHE, WSQUASHFS_BACKUP_DIR
Emplacements des sauvegardes, du cache et des archives.
WSQUASHFS_BATOCERA_SAVES
Dossier de SAVEDIR/SAVEFILES (défaut : saves/ à côté de roms/).
WSQUASHFS_OVERLAY
auto (défaut), fuse ou kernel (sans repli).
WSQUASHFS_DXVK=0, WSQUASHFS_D7VK=0
Désactive DXVK ou d7vk pour tous les jeux (le réglage d'un jeu l'emporte).
WSQUASHFS_HIDRAW, WSQUASHFS_VIRTUAL_DESKTOP
Valeur par défaut de HIDRAW et VIRTUAL_DESKTOP pour tous les jeux.
WSQUASHFS_NVAPI, WSQUASHFS_VKREFLEX, WSQUASHFS_FSR, WSQUASHFS_FSR4
Valeur par défaut de NVAPI, VKREFLEX, FSR et FSR4 pour tous les jeux.
WSQUASHFS_UMU=0
Lance le Wine d'un Proton directement, sans umu.
WSQUASHFS_DXVK_DIR, WSQUASHFS_VKD3D_DIR, WSQUASHFS_D7VK_DLL
Emplacements de DXVK, VKD3D-Proton et d7vk.
Installer le lanceur sur un PC 
curl -fsSL https://raw.githubusercontent.com/Gunnm92/wsquashfs-launcher/main/install.sh | bash

Dépannage

Les problèmes fréquents et leur solution. Pour un jeu qui ne démarre pas, commence par le guide.

Le jeu ne se lance pas
Fiche → Lancement d'essai : rapport avec fenêtres, erreurs et capture. En ligne de commande : relancer depuis un terminal pour lire les erreurs Wine, et vérifier la commande avec --info.
failed to open umu.exe
Les liens du prefix pointent vers un runner absent. Fiche → Infos → Liens du runner → Analyser, puis la réparation proposée. Voir Runner joint.
fusermount3: mount failed: Operation not permitted
FUSE est bloqué dans le conteneur : le lanceur passe en mode copy (plus lent au premier lancement). Pour l'overlay : --device /dev/fuse --cap-add SYS_ADMIN.
Overlay noyau indisponible
Le jeu marche quand même, sous fuse-overlayfs. --doctor donne la cause : squashfuse antérieur à 0.5 (Debian 12), namespaces refusés (seccomp de Docker : --security-opt seccomp=unconfined ; AppArmor d'Ubuntu 24.04 ; user.max_user_namespaces=0), ou sauvegardes sur un système de fichiers sans attributs user.*.
Make sure that your X server is running…
Wine ne trouve pas l'affichage : vérifier $DISPLAY et autoriser l'utilisateur avec xhost +SI:localuser:$(id -un).
Écran noir ou affichage très lent
