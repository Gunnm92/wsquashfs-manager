    Construire une image

    Principe

    Une image .wsquashfs est un dossier compressé en lecture seule (format Batocera pour les jeux Windows). Le lanceur la monte, ajoute par-dessus une couche de sauvegardes propre au jeu, puis lance la commande de son autorun.cmd. L'image n'est jamais modifiée : tout ce que le jeu écrit va dans ses sauvegardes.

    La construction dépend du type de l'image, déterminé par ce qui se trouve à sa racine : system.reg (prefix Wine), config_info (prefix Proton) ou rien de tout cela (jeu seul).

    • Construire : wsquashfs-launcher --pack <dossier> (zstd), ou l'onglet « Dossiers à empaqueter » ici, qui propose aussi l'autorun. Vérifier ensuite avec --info.
    • Ne jamais abîmer un original : la nouvelle image est construite à côté et ne remplace l'ancienne qu'une fois terminée.

    Prefix Wine (Batocera)

    Reconnu par system.reg à la racine. Jeux arcade (TeknoParrot, Taito Type X, Sega…), format natif de Batocera.

    MonJeu.wine/
├── autorun.cmd
├── system.reg   user.reg   userdef.reg
├── drive_c/
│   └── MonJeu/game.exe
└── *.reg        (facultatif : importés au lancement)
    DIR=drive_c/MonJeu
CMD=game.exe
GAME_VERSION=1.04
REM facultatif : WINE=tkg | system, ARCH=win32
    • Runner : wine-tkg par défaut. WINE=system pour un jeu 32 bits qui ne passe qu'en WoW64 (GTI Club – Supermini Festa).
    • Racine de l'image = le prefix. DIR est relatif à cette racine.
    • Reste lisible par Batocera tel quel : il ignore les clés qu'il ne connaît pas (GAME_VERSION, WINE…).

    Prefix Proton

    Reconnu par config_info à la racine (prefix créé par Heroic, Steam ou umu). Jeux PC récents.

    MonJeu.wine/
├── autorun.cmd
├── config_info   version   tracked_files
├── pfx -> .     (lien créé par Proton)
├── system.reg …
└── drive_c/MonJeu/Bin/game.exe
    DIR=drive_c/MonJeu/Bin
CMD=game.exe
PROTON=UMU-Proton-10.0-4   (facultatif)
    • Runner : le Proton qui a créé le prefix (1re ligne de config_info), sinon le repli décrit dans Choix automatique du runner. Lancé via umu.
    • PROTON=<nom> impose un Proton ; introuvable = erreur, sans repli silencieux.
    • Les DLL de Proton sont des liens vers le runner (PROTON_DLL_COPY vide), pas des copies.
    • Batocera n'a pas umu : ces images n'y sont pas prévues.

    Jeu seul

    Ni system.reg ni config_info : seulement les fichiers du jeu.

    MonJeu/
├── autorun.cmd
└── game/
    └── run me.exe
    CMD="game/run me.exe" --arg
    • Le prefix est créé au premier lancement par Proton via umu, dans les sauvegardes : l'image reste légère.
    • CMD est relatif à la racine ; guillemets si le chemin contient des espaces.
    • WINE=tkg pour garder un prefix Wine au lieu de Proton. Un prefix Wine déjà présent dans les sauvegardes reste sous Wine (Proton ne sait pas le convertir) : réinitialiser les sauvegardes du jeu pour passer sous Proton.

    Runner joint à l'image

    Pour un jeu qui ne marche qu'avec un runner précis (Proton modifié comme DenuvOwO pour Anno 117, Wine particulier d'un jeu arcade). Se combine avec les trois types ci-dessus. L'image devient autonome : rien à installer sur la machine.

    MonJeu.wine/                 → --pack habituel, sans option
├── autorun.cmd    PROTON=DenuvOwO-cachyos-11.0
├── runners/
│   └── DenuvOwO-cachyos-11.0/     le dossier du runner tel quel
│       ├── proton                (Proton : proton + files/bin/wine)
│       └── files/bin/wine        (Wine : bin/wine)
└── drive_c/ …
    • PROTON=<nom> ou WINE=<nom> cherchent d'abord runners/<nom>/ (aussi runners/wine-<nom>/, casse ignorée), puis les runners de la machine. Sans clé, un runner seul dans runners/ est utilisé.
    • Priorité : --wine > runner joint > runners de la machine.
    • Utilisé en lecture seule depuis l'image : Proton n'écrit rien dans les sauvegardes, et son chemin ne change pas d'un lancement à l'autre (sinon Proton refait la mise en place du prefix).
    • Runner nommé introuvable (ni dans l'image ni sur la machine) : le lancement s'arrête avec un message, le jeu ne part pas sous un autre runner.
    • À réserver aux runners propres à un jeu. Un Proton standard (UMU-Proton, GE-Proton, proton-cachyos) n'a pas à être joint : le choix automatique de la machine reste meilleur. Compter ~250 Mo compressés pour un Proton.
    • RUNNER= ne sert qu'aux chemins absolus de la machine ; un chemin relatif est refusé.
    • Batocera ignore runners/ (seulement de la place). --info et la colonne Runner indiquent « joint ».
    Liens du prefix. Dans un prefix Proton, les DLL de Wine sont des liens vers le runner. Avant --pack, ils doivent pointer en relatif dans runners/<nom>/ (ex. ../../../runners/<nom>/files/lib/wine/…). Un lien vers un autre emplacement (ancien runner/, compatibilitytools.d de la machine) est cassé ailleurs, et Proton ne répare pas un lien cassé : le jeu ne démarre plus (failed to open umu.exe).
    Vérifier : find MonJeu.wine -type l -lname '*compatibilitytools.d*' doit être vide.

    Préparation et correctif du jeu : dans le runner (Proton)

    Un Proton joint peut porter le correctif du jeu : un protonfix que Proton exécute avant chaque lancement (Call of Duty MW4).

    runners/GE-Proton11-9/protonfixes/gamefixes-umu/umu-mw4.py
    PROTON=GE-Proton11-9
ENV=GAMEID=umu-mw4
    • main() du protonfix : préparation (un sys.exit(1) arrête le lancement), puis un fil pour le patch à chaud. Ce fil vit dans le processus Proton jusqu'à la fin du jeu, donc rien ne reste derrière.
    • N'agir que si l'exécutable du jeu est dans sys.argv : umu sert aussi à d'autres commandes (reg, wineboot).
    • Sinon, pour tout runner, Wine compris : PRE= et ATTACH= de l'autorun (Clés de base).

    Clés de base

    Fichier à la racine de l'image, au format Batocera : une paire CLÉ=valeur par ligne, REM pour un commentaire, fins de ligne DOS tolérées. Batocera ignore les clés qu'il ne connaît pas : l'image reste compatible.

    CléRôleExemple
    CMD obligatoireExécutable et arguments, guillemets si le nom contient des espaces."My Game.exe" -fullscreen
    DIRDossier de l'exécutable, relatif à la racine de l'image. Vide : racine.drive_c/Game
    GAME_VERSIONVersion du jeu empaqueté, affichée au lancement, par --info, --pack, --install et ici. Ignorée par Batocera.v2.1.0 GOG
    PRECommande lancée une fois avant le jeu, dans DIR, avec l'utilisateur et l'environnement du jeu (WINEPREFIX…). Un échec arrête le lancement. Sert à préparer des fichiers que l'image ne peut pas contenir tels quels.sh pre.sh
    ATTACHCommande lancée pendant le jeu, une fois son processus trouvé (sans délai maximal) ; GAME_PID contient son PID. Elle accompagne le jeu jusqu'à la fin de tous ses processus Wine, a ensuite 5 s pour finir seule, puis est arrêtée avec tout ce qu'elle a lancé.sh attach.sh
    ATTACH_PROCESSProcessus attendu par ATTACH (15 caractères au plus, comme le noyau). Défaut : l'exécutable de CMD ; à renseigner quand CMD est un lanceur qui démarre le vrai jeu.DOA5A.exe
    PRE et ATTACH exécutent des commandes Linux sur la machine, hors de Wine : à n'utiliser que pour des images de confiance. Ni l'une ni l'autre n'est lancée par --exec. Batocera les ignore : un jeu qui en dépend n'y fonctionnera pas tel quel.

    Wine et Proton

    CléRôleExemple
    WINEWine joint à l'image (runners/<nom>/), sinon /opt/wine-<nom>/bin/wine ou un runner installé ; system : le Wine WoW64 du système. Introuvable : erreur.tkg, 9.0, system
    PROTONProton joint à l'image, sinon un Proton de Heroic ou Steam (nom du dossier ou version). Introuvable : erreur, pas de repli sur un autre Proton.UMU-Proton-10.0-4, GE-Proton8-25
    RUNNERChemin absolu d'un binaire wine de la machine. Un runner joint passe par runners/ et PROTON/WINE./opt/wine-custom/bin/wine
    ARCHArchitecture du prefix ; déduite du prefix existant, win64 sinon.win32, win64
    LANGLangue du jeu (LC_ALL).fr_FR.UTF-8
    ENVVariables d'environnement supplémentaires, séparées par des espaces.VAR1=a VAR2=b
    HIDRAW1 : manettes Sony par hidraw, pour un jeu qui gère la DualSense lui-même (sans Steam Input) ; repli XInput si illisible. Une DualSense Bluetooth (celle de Sunshine) est présentée en USB par dualsense-usb-bridge : les libScePad de 2022 (F1 22) refusent la Bluetooth. bt : DualSense Bluetooth en direct, pour les haptiques Bluetooth (Until Dawn). Défaut : XInput, comme Batocera. Sous GE-Proton, le mode XInput passe aussi par hidraw (PROTON_SONY_HIDRAW_XINPUT=1, posé par le lanceur).1, bt

    Touches clavier : fichier <jeu>.wsquashfs.keys à côté de l'image (mappage manette → clavier, signalé dans la colonne Extras).

    Choix automatique du runner

    Sans WINE, PROTON, RUNNER, runner joint ni --wine :

    • Prefix créé par Proton (config_info) : la même version de Proton, cherchée dans ~/.config/heroic/tools/proton, ~/.local/share/Steam/compatibilitytools.d, ~/.steam/root/compatibilitytools.d et /usr/share/steam/compatibilitytools.d. Absente : proton-cachyos, puis l'UMU-Proton le plus récent, puis GE-Proton, puis n'importe quel Proton installé.
      Le jeu est lancé via umu (umu-run du paquet umu-launcher, à défaut celui de Heroic) avec le script proton, comme Heroic : Proton gère le prefix, DXVK, VKD3D et NVAPI. Sans umu, le Wine du Proton est lancé directement, avec un avertissement (certains jeux ne s'affichent pas) ; WSQUASHFS_UMU=0 force ce mode.
      Les DLL que Proton copie d'ordinaire dans chaque prefix (d3dx9, msvcp, xaudio… ~190 Mo par jeu) y sont des liens vers Proton (PROTON_DLL_COPY vide) ; ENV=PROTON_DLL_COPY=<motifs> pour un jeu qui doit les remplacer.
    • Jeu seul : prefix créé par Proton via umu (proton-cachyos, sinon l'UMU-Proton le plus récent, sinon GE-Proton). proton-cachyos et UMU-Proton d'abord : leur SDL gère la DualSense en manette XInput, vibration comprise ; GE-Proton la force en hidraw, sans vibration en mode XInput. WINE=tkg pour garder wine-tkg.
    • Autres prefixes (arcade Batocera) : wine-tkg, puis wine-ge/lutris, puis wine-proton, puis le Wine du système ; les chemins Batocera (/usr/wine/…) sont pris en charge. Certains jeux 32 bits échouent sous wine-tkg (non WoW64) mais passent avec le Wine WoW64 du système : WINE=system.

    Le lanceur ramène la pile à 8 Mo si elle est illimitée (cas de Docker sur Unraid) : sans cela proton-cachyos ne démarre pas, et les jeux 32 bits sous wine-tkg manquent de mémoire.

    Sauvegardes

    Tout ce que le jeu écrit va dans saves/<jeu> (la couche au-dessus de l'image), jamais dans l'image. Comme Batocera, deux clés relient en plus un dossier ou des fichiers à saves/<système>/<jeu>, à côté de roms/ :

    CléRôleExemple
    SAVEDIRDossier de sauvegarde du jeu. Les sauvegardes empaquetées y sont copiées sans jamais écraser l'existant.drive_c/game/saves
    SAVEFILESFichiers de sauvegarde, séparés par ;, relatifs au prefix.drive_c/game/save.dat;drive_c/game/cfg.ini

    Rendu et optimisations

    CléRôleDéfaut
    DXVKDirect3D 8 à 11 → Vulkan. 0 : rendu OpenGL de Wine (wined3d), qui tombe sur le rendu logiciel sous Xwayland + NVIDIA. Sous Proton, seul un DXVK=0 explicite change quelque chose.1 (contrairement à Batocera)
    VKD3DDirect3D 12 → Vulkan (vkd3d-proton). Sans effet sur un jeu qui ne charge pas d3d12.dll.1
    D7VKDirectDraw / Direct3D 7 → Vulkan (d7vk). Sans effet sur un jeu qui ne charge pas ddraw.dll.1 si installé
    VIRTUAL_DESKTOPBureau virtuel Wine : évite les plantages du gestionnaire de fenêtres quand le jeu change la résolution.aucun
    ESYNCSynchronisation par événements (WINEESYNC).0
    FSYNCSynchronisation par futex (WINEFSYNC), noyau compatible requis.0

    Un DXVK ou un VKD3D-Proton absent de la machine désactive la clé correspondante, avec un avertissement au lancement.

    Surcharge sans reconstruire

    Un fichier <jeu>.wsquashfs.autorun posé à côté de l'image, au même format, permet d'essayer un réglage tout de suite. Une clé qui y figure l'emporte sur celle de l'image, CLÉ= vide la ramène au défaut du lanceur, les autres viennent de l'image. Le lancement et --info l'annoncent (« Surcharge : … »).

    # Le Jeu.wsquashfs.autorun
GAME_VERSION=1.2.0
HIDRAW=1

    Batocera ne lit pas ce fichier : une fois le réglage validé, l'inscrire dans l'image (une action dans la fiche de l'image) et supprimer la surcharge.

    Exemples

    Jeu simple

    DIR=Game
CMD=game.exe -fullscreen

    Chemin avec espaces

    DIR=drive_c/Program Files/My Game
CMD="My Game.exe" --lang fr

    Jeu 32 bits ancien, Wine du système

    CMD=oldgame.exe
ARCH=win32
WINE=system

    Proton imposé, DualSense gérée par le jeu

    DIR=drive_c/Game/Bin
CMD=game.exe
PROTON=GE-Proton9-20
HIDRAW=1

    Lanceur intermédiaire + outil pendant le jeu

    CMD=Launcher.exe

ATTACH_PROCESS=Game.exe

    Résolution fixe, fichier batch

    CMD=start.bat
VIRTUAL_DESKTOP=1920x1080

    Lanceur wsquashfs-launcher

    Commandes

    Aucun privilège requis : l'image est montée en utilisateur, y compris les paquets Batocera dont les fichiers appartiennent à root. Sauvegardes et prefix appartiennent à l'utilisateur qui lance le jeu ; sudo reste accepté mais n'apporte rien.

    wsquashfs-launcher [--wine <version>] <jeu.wsquashfs>
    Lance le jeu (commande de l'autorun.cmd).
    wsquashfs-launcher [--wine <version>] <dossier du jeu>
    Lance un jeu installé (dossier contenant autorun.cmd) sur place, sans montage : le jeu écrit directement dans son dossier.
    --exec <jeu.wsquashfs> <programme> [arguments…]
    Lance un autre programme dans le prefix du jeu : un exécutable du jeu (chemin relatif au prefix ou au DIR, casse ignorée, ex. JConfig.exe, drive_c/teknoparrot/TeknoParrotUi.exe) ou un outil Wine (winecfg, regedit, cmd, explorer, control joy.cpl…). Combinable avec --wine. PRE/ATTACH ne sont pas lancés.
    --mount <jeu.wsquashfs> · --umount [<jeu.wsquashfs>]
    Monte le jeu et le laisse monté pour le modifier à la main ; les changements vont dans ses sauvegardes, jamais dans l'image. --umount démonte un jeu, ou tous ; sur un jeu en cours, il arrête la partie.
    --pack <Jeu.wine> [sortie.wsquashfs]
    Crée un .wsquashfs (zstd) à partir d'un dossier. Image existante : confirmation au terminal (et proposition de réinitialiser ses sauvegardes), refus sans terminal ; l'ancienne n'est remplacée qu'une fois la nouvelle construite. Un runner propre au jeu se joint en le copiant dans runners/<nom>/.
    --install <jeu.wsquashfs> [dossier]
    L'inverse de --pack : extrait le jeu dans <dossier>/<Jeu> (défaut : à côté de l'image), pour jouer sans FUSE. L'image est conservée, ses sauvegardes ne sont pas reprises, un dossier existant n'est jamais écrasé. EmulationStation n'affiche que les .wsquashfs.
    --info <jeu.wsquashfs | dossier>
    Version (GAME_VERSION), type de prefix, runner (joint ou non), commande, surcharge et taille, lus sans monter l'image.
    --list
    Jeux connus : état (en cours, verrouillé, monté), version, taille des sauvegardes et image d'origine.
    --clean
    Supprime les copies de travail (cache) et les doublons des sauvegardes : fichiers du jeu recopiés sans modification (jeu qui ouvre ses données en écriture : 2,7 Go pour Streets of Rage 4), DLL que Proton recopie à chaque lancement. Tout ce que le jeu a écrit est gardé ; jeux en cours exceptés.
    --clear [jeu]
    Radical : ne garde que drive_c/users des sauvegardes (de tous les jeux, ou d'un seul). Le prefix est recréé au lancement suivant ; scores et réglages écrits ailleurs (jeux arcade, dossier du jeu, registre) sont perdus. Chaque jeu est archivé (--backup) avant ; sans archive, il n'est pas touché. Confirmation au terminal.
    --backup [jeu]
    Archive les sauvegardes dans ~/.local/share/wsquashfs/backups/<jeu>-AAAAMMJJ-HHMMSS.tar.zst ; jeux en cours exceptés. Restauration, jeu arrêté : 
    tar -C ~/.local/share/wsquashfs/saves --xattrs --xattrs-include='user.*' -xpf <archive>
    --doctor
    Vérifie l'installation : FUSE, overlay noyau, Wine/Proton et runners, umu, DXVK, VKD3D, d7vk, manettes (hidraw, dualsense-usb-bridge), dossiers. Chaque point est marqué ✓, ✗ (avec la conséquence) ou – (facultatif). Code 1 si aucun jeu ne peut être lancé.
    --help
    Affiche l'aide du lanceur.

    Option --wine <version>

    Impose un runner : nom (ou partie du nom) d'un runner installé dans /opt, /usr/wine, ~/.local/share/wsquashfs/wine ou un dossier Proton de Heroic/Steam, chemin d'un binaire wine, ou system. Passe avant tout, runner joint compris. Un Proton sur un jeu à prefix Proton ou sans prefix est lancé via umu, comme PROTON= ; sur un prefix Wine (Batocera), son Wine est lancé directement.

    Outils extérieurs

    MangoHud, gamemode… se placent devant la commande ; leurs variables sont transmises au jeu, y compris lancé en root (jeux 32 bits : lib32-mangohud).

    mangohud wsquashfs-launcher MonJeu.wsquashfs

    Modes de montage

    Choisis automatiquement à chaque lancement :

    ModeQuandSauvegardes
    overlay noyauPar défaut si l'environnement le permet : overlay du noyau dans un namespace utilisateur (Linux ≥ 5.11, squashfuse ≥ 0.5).Isolées dans saves/<jeu>
    overlay FUSERepli : squashfuse + fuse-overlayfs. Toujours utilisé par --mount, dont le montage doit survivre au lanceur.Isolées dans saves/<jeu>
    copyFUSE bloqué (conteneur sans CAP_SYS_ADMIN) : squashfuse ou unsquashfs, copie de travail en cache, relances instantanées tant que l'image ne change pas.Dans la copie de travail
    dossierJeu installé (--install) lancé sur place, sans FUSE.Dans le dossier du jeu

    Overlay noyau

    Le lanceur se relance dans un namespace utilisateur (unshare --map-current-user --mount --keep-caps), y monte l'image avec squashfuse_ll -o uid=,gid= (tous les fichiers appartiennent alors à l'utilisateur, même ceux de root des paquets Batocera), puis l'overlay du noyau par-dessus. Wine est lancé sans les capacités du namespace.

    • Une seule couche FUSE au lieu de deux : lectures aléatoires en parallèle (chargement d'un niveau) environ 5 fois plus rapides, mesuré sur Tempest Rising ; lecture séquentielle pure plus lente (1,5 Go/s contre 3,7 Go/s).
    • Sauvegardes écrites à la vitesse du disque.
    • Montages invisibles hors du namespace, disparus avec lui : rien d'orphelin après un plantage.
    • Tout échec retombe sur fuse-overlayfs (namespaces refusés, squashfuse trop ancien, sauvegardes sans attributs user.* ou sur un overlay…). --doctor dit pourquoi.
    • Les deux overlays partagent les mêmes sauvegardes : les marqueurs propres à fuse-overlayfs (.wh..wh..opq, .wh.<nom>) sont convertis avant chaque montage noyau.

    Overlay FUSE

    squashfuse monte l'image en lecture seule, fuse-overlayfs la combine avec saves/<jeu> (seules les modifications) ; son répertoire de travail est dans saves/.work/<jeu>, toujours sur le même disque que les sauvegardes, sans quoi Wine ne peut rien y écrire. Démontage automatique à la sortie.

    Installation

    curl -fsSL https://raw.githubusercontent.com/Gunnm92/wsquashfs-launcher/main/install.sh | bash

    L'installeur détecte la distribution — Debian/Ubuntu (apt) ou Arch, CachyOS, Manjaro, EndeavourOS (pacman) — et installe les paquets manquants : squashfuse, squashfs-tools, fuse-overlayfs, attr, zstd, bibliothèques 32 bits (dépôt [multilib] sous Arch, avec la version 32 bits des pilotes Vulkan), MangoHud en option. Puis il propose :

    • wine-tkg / wine-ge (jeux arcade Batocera) dans ~/.local/share/wsquashfs/wine ;
    • umu-run et un Proton (proton-cachyos sous CachyOS, sinon UMU-Proton, empreinte vérifiée) — nécessaires aux jeux PC récents, inutiles pour l'arcade seule ;
    • DXVK, VKD3D-Proton et d7vk dans ~/.local/share/wsquashfs/.

    Il termine par --doctor. Options : --dry-run (montre sans rien modifier), --yes (sans questions), --uninstall. Le script seul s'installe aussi par make install ou en copiant wsquashfs-launcher dans le PATH.

    Docker : make build-docker puis ./run-docker.sh MonJeu.wsquashfs. L'image contient wine-tkg, le Wine de Debian, DXVK, VKD3D-Proton et d7vk, pas de Proton ; sauvegardes et cache dans des volumes.

    Dépannage

    Le jeu ne se lance pas
    Le relancer depuis un terminal pour lire le récapitulatif et les erreurs Wine ; vérifier la commande avec --info.
    fusermount3: mount failed: Operation not permitted
    FUSE bloqué dans un conteneur : le lanceur passe en mode copy (unsquashfs, paquet squashfs-tools). Pour l'overlay : --device /dev/fuse --cap-add SYS_ADMIN.
    Overlay noyau indisponible
    --doctor et chaque lancement donnent la cause ; le jeu marche quand même sous fuse-overlayfs. Causes fréquentes : squashfuse antérieur à 0.5 (Debian 12) ; namespaces refusés (profil seccomp de Docker — privileged: true ou --security-opt seccomp=unconfined —, AppArmor d'Ubuntu 24.04 via kernel.apparmor_restrict_unprivileged_userns, user.max_user_namespaces=0) ; sauvegardes sur un système de fichiers sans attributs user.* ou sur un overlay (en conteneur : sur un volume).
    Make sure that your X server is running…
    Wine ne trouve pas l'affichage : vérifier $DISPLAY et autoriser l'utilisateur avec xhost +SI:localuser:$(id -un).
    failed to open umu.exe
    Liens du prefix vers un runner absent : voir Runner joint.
    Un jeu reste monté
    --umount (tous les jeux).
    Repartir de zéro pour un jeu
    --clear "MonJeu" ne garde que drive_c/users, après archive. En mode copy : supprimer ~/.cache/wsquashfs/wine/<jeu>, ou --clean.
    Socket ICMP refusé (Yu-Gi-Oh! 5D's DT6)
    Un jeu qui plante faute de pouvoir « pinger » dans un conteneur non privilégié : relais fakeping (dinput8.dll) fourni avec le lanceur, signalé dans la colonne Extras.
